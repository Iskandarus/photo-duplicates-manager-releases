# Contract changelog

Every change to a published contract is recorded here, in one file, because an implementer should have one place to read rather than three. The rules that govern what may change in a minor, how long a version stays supported and how a removal is announced are in [`docs/version-compatibility.md`](version-compatibility.md) (#174).

One version line, and one document:

| Line | Declared in | Machine-readable document |
| --- | --- | --- |
| Core API | the `PDM-Core-Version` header, negotiated per request | [`core-api.v1.yaml`](core-api.v1.yaml) |

There were three. `resource-manager-ui-protocol.v1.schema.json` described a postMessage protocol between PDM and a resource manager's own page, mounted in a frame; it was **retired at 1.0 without ever being implemented** (#197). `resource-manager-api.v1.yaml` described what a resource manager served to PDM; it was **withdrawn at 1.3** (#278), because PDM makes no call to a resource manager at all and there is nothing left for one to serve. The rows of both are kept because this file is the history of what was published, and a document that was withdrawn is exactly the kind of thing somebody has to be able to look up.

Entries are grouped by the product release that shipped them, because that is the unit a user updates and the unit a release note describes. Each row says what changed and what it means for an implementer who does nothing. The second half is the part that matters: a minor is additive, so the honest answer is almost always "nothing", and the rows where it is not are the ones worth reading twice.

The `info.version` of the OpenAPI document and the newest entry for that line here must agree. A contract change that is not in this file is a bug, and that is checked rather than hoped for: `ContractHygieneTests` in `PDM.API.Tests` reads this file and the document, and `.github/workflows/contracts.yml` lints the document per pull request (#151, moved here by #278 when the conformance suite retired with the contract it checked).

| Core API | 3.0 | **The channel `POST /v1/events` relayed into is gone, and the operation with it (#318).** **Removed** - `POST /v1/events`, the scope `events:publish`, the four kinds `account_connected`, `account_disconnected`, `enumeration_progress` and `resource_manager_unavailable` with their request schemas, and the two limits that bounded them, `eventsPerMinute` and `maxEventBytes`. Nothing is added and nothing else changes. **The operation was defined as a relay** (#161): a manager said one of four things and PDM put it on the user's live notification channel. That channel is a SignalR service PDM ran for its own pages, and **it has had no subscriber since #251** - the app host draws no working area, and the screens that do belong to each manager's own frontend, on that manager's own origin, where PDM's hub is not something a page may reach. So the operation relayed into nothing, which is a published promise that had quietly stopped being true. **Three of the four kinds had nowhere else to arrive and the fourth was one number twice.** `enumeration_progress` also refined the stored progress reading, and 2.3 gave that same number a better door on a call the caller is already making - `expectedTotal` on a declaration, sent by the walker that is counting rather than by a second message about the same walk. **No overlap is owed, and this is where that is written down rather than inferred.** [`docs/version-compatibility.md`](version-compatibility.md) section 3.2 asks twelve months between majors unless there is nobody to overlap with, and there is nobody: no `sdk-v*` tag has ever been cut, so the bundle #192 built has never left this private repository and no 2.x client can exist outside it - the same ground #197 and #278 stood on. **It is the last version that ground is available for**, and that is the reason this was taken now rather than left: the first publication spends the waiver for good. | **A client that asks for 2.x is refused by name** with `400 unsupported_core_version` naming both versions, which is what a major means. Ask for 3.0. If you published events, there is nothing to move them to and nothing was hearing them: tell your own frontend directly, over your own connection to it, which is what all four built-in managers already do - none of them was ever granted `events:publish`, and the SDK's scan driver asks the token for that scope before it sends and finds it absent. Everything else in this document is untouched: the same operations, the same shapes, the same scopes minus one, and `GET /v1/stream` still carries what PDM has to say. |
| Core API | 2.4 | **A file the scan could not read is counted, and the two kinds are told apart (#226).** Two response fields on a result, `totalUnsupportedImages` beside the `totalBrokenImages` that has been declared here since 1.0, and one on a `ResultImage`, `errorCode`. Nothing was ever answered in either of the two places this API had already set aside for it: `totalBrokenImages` was always `0` and `brokenImages` on the first page of a result's groups was always absent, so a library holding files this deployment cannot decode scanned quickly and produced a result with nothing visibly missing from it. **The counts are the whole scan and the list is bounded**, which is the one thing worth reading twice: fewer entries than `totalBrokenImages` is the bound and not a contradiction, because which files and how many are different questions and only the first has a size a person can use. **The two kinds are one fact noticed at two moments.** A declared `mimeType` this deployment cannot decode is refused before any bytes move (2.2) and a file that declared nothing and turns out to name no container PDM carries is found at the far end of the pipeline; both are `unsupported_format`, because it would be a poor API that called one thing two names depending on when it was noticed. `unreadable_bytes` is the other kind: the file announced a format that is decoded here and no decoder would open it. **They are worth wording differently** - a photograph in a format nothing here reads is whole wherever it lives and converting it is something somebody can do, while a damaged file has nothing to convert. **A transfer that never arrived is not either of them**: that is a transport problem, the file is probably fine, and it stays where it was, in `notices`. | Nothing. Additive: two response fields, one enum, no new operation and no new scope, and a client that keeps asking for 2.3 keeps being served 2.3 - where `totalBrokenImages` reads `0` for every result, which is what it has always read. Take it up by showing the count on a result and, where you show the files, reading `errorCode` rather than `error`: the second is English and meant for a person. An entry in `brokenImages` carries your own `imageRef` and nothing that was measured - there are no dimensions, because the file did not open - so draw it from what you know about the file yourself, which is everything. Its `imageId` is accepted by no operation. |
| Core API | 2.3 | **A scan says how many photographs there are, and how fast it is going (#227).** One optional request field, `expectedTotal` on a declaration, and one response field, `itemsPerSecond` on a reading. **The number is yours and it could never have been PDM's**: the core receives one batch at a time and never materialises a folder (#163), so counting there would be your walk performed twice, at PDM's expense, over the wire. What it replaces is a progress dialog that showed a count which only climbed - reported from the field as a bug three times over, because a running discovery count and a total look identical on screen and a scan of a photo library is measured in hours. **A converging total is a total.** `totalItems` is now present as soon as a count arrives and `percent` with it, while `isTotalKnown` keeps the narrower meaning it always had - the walk is over, this will not move again - so the two are separate answers and a client that needs to say whether a number is settled reads the second. **Being wrong is not an error**: nothing loops until your count is reached, no search completes because of it, and it is never reported below what you have actually declared, so a count that turns out low slows the bar down rather than taking it past the end, and one that turns out high leaves it arriving late. Send a corrected number whenever you have one. Two more things moved with it and neither is new vocabulary. `percent` is now the whole search rather than the running stage, which is a **defect fixed rather than a meaning changed** - it was `processedItems` over `totalItems`, and those are the counters of whichever stage is running, so embedding filled the bar to the end and comparing started it again from nothing. And `itemsPerSecond` is derived from readings rather than stored, smoothed over a short window, present-and-null where there is not enough history and **zero where nothing is moving** - which is the answer that stops a long quiet stretch reading as a frozen application. | Nothing. Additive: one optional request field, two response fields, no new operation and no new scope, and a client that keeps asking for 2.2 keeps being served 2.2. Take it up by counting your own resource before you walk it - a listing pass with no file opened, nothing hashed and nothing downloaded, in front of a scan that downloads and embeds every photograph it finds - and sending the number on every declaration. If your service will simply answer the question, ask it; if it will not, walk and count, which is what all four built-in managers do. A manager that sends nothing keeps exactly the behaviour it has: no total, no percentage, and a screen that says "found N so far". If you draw a bar, draw it from `percent` and read `isTotalKnown` before you call a number final. |
| Core API | 2.2 | **What PDM can decode, published as one list (#207).** `GET /v1/capabilities` gains `formats`, with `mediaTypes` and `extensions`, and a declared item whose `mimeType` names an image format absent from it is `rejected` with the new per-item code `unsupported_format` before any bytes are asked for. **It exists because there were four lists and no right answer.** Each resource manager decided for itself what it would enumerate - six extensions on a local disk, ten through Dropbox and OneDrive, six media types through Google Drive and a different six - so the same photograph was visible through one manager and invisible through another. What a manager knows is what its own service can serve; what PDM can decode is a fact about the pipeline that decodes, and the pipeline is one pipeline. **The list itself is what the issue was opened about**: HEIC and HEIF (the iPhone default since iOS 11), TIFF, and ten RAW families - DNG, CR2, CR3, NEF, ARW, RAF, ORF, RW2, PEF, SRW - which are read at their embedded preview rather than demosaiced, so a RAW file costs less to scan than the JPEG beside it and not more. **Silence is deliberately not a refusal.** An item declaring no `mimeType`, or `application/octet-stream`, is asked for and identified from its own leading bytes; only a named image format PDM does not carry is refused, because a manager whose filesystem told it nothing must not lose a photograph over that. | Nothing. Additive: one response field, one per-item error code, no new scope, no new operation, and a client asking for 2.1 keeps being served 2.1 - where the field is simply absent and nothing is refused for its format. Take it up by reading `formats` once per scan and filtering your walk against it, in whichever of the two spellings suits your source. **Do not pin a copy**: the list grows in minors, and a manager holding 2.2's copy is one whose users cannot scan whatever 2.3 adds. If you already filter by a list of your own, widen it or drop it - an item you never declare is a photograph PDM cannot tell anybody about. |
| Core API | 2.1 | **Duplicates while the scan is still running (#295).** One operation, `GET /v1/searches/{searchId}/groups`, and one event beside it, `search_groups`, both under scopes that already exist (`searches:read`, `stream:subscribe`). It restores something that used to work rather than adding something new: PDM's grouping stage has taken a snapshot of the duplicate groups it has formed roughly once a second since the live preview shipped, and it went to PDM's own notification hub - which the screen that renders duplicates stopped listening to when it moved to the resource manager's own origin. So the snapshots were computed, addressed to a channel with no subscriber, and dropped. **What is answered is a snapshot, not an accumulation**: each replaces its predecessor entirely, so re-reading never double-counts, and `groupId` is stable across the snapshots of one search so a page redraws instead of remounting every tile. That `groupId` is **not** the identifier the saved result will carry and no operation accepts it. **The event carries the counts and not the groups**, for the reason nothing else on that channel carries bulk: a snapshot of a large library is thousands of references and the connection drops for a subscriber that falls behind rather than waiting for it. An **empty page is an ordinary answer** - a scan before its grouping stage, one past it, and a search whose result is written all have no live groups. And the set a caller watches appear is the set the saved result contains plus whatever the last batch added: both are built from the same pairs, and the last snapshot is taken before the result is persisted. | Nothing. Additive: a new path, a new event kind, no new scope, and a client that keeps asking for 2.0 keeps being served 2.0. Take it up when you would rather not show somebody an empty page for the length of a scan: subscribe as you already do, read the page when `search_groups` arrives, ignore the `groupId` except as a rendering key, and switch to `GET /v1/results/{resultId}/groups` when the search ends. |
| Core API | 2.0 | **`threshold` is a similarity, and was documented as a distance (#298).** A correction to 2.0 before it is published rather than a version of its own: the field has been described here as "distance below which two images are considered duplicates" since #166, with a default of `0.03`, and no build has ever implemented it that way - the engine compares cosine similarity and calls a pair duplicates when `similarity >= threshold`. So a caller who read the document and sent `0.03` was asking for every pair of photographs it had sent, and got one group holding all of them. Nothing in between could catch it, because both units are numbers between 0 and 1 and that is the only thing anything checked. The description now says what the engine does and the default is `0.97`. **The document is corrected rather than superseded** because 2.0 has not been published: there is no `sdk-v*` tag, so the row below is the intention and not yet the event, and the twelve months of [`docs/version-compatibility.md`](version-compatibility.md) section 3.2 start from a document that says the truth. | **Check what you send.** If you send a threshold at all, it is a cosine similarity: `0.97` is a strict search and near-identical photographs, `0.90` is loose, and anything below about `0.5` puts your whole library in one group. If you omit it you now get `0.97` where you used to get `0.03`, which is the difference between a result somebody can use and one group of everything. Nothing else moved: the field, its range and its place in the request are unchanged. |

From the day this bundle is published that ground is gone, so **2.0 is the first version that inherits the twelve months**, and a 3.0 owes it in full. | Nothing. The document is unchanged, and a client written against 2.0 keeps working. | Core API | 2.0 | **Served (#278).** The row below wrote 2.0 down before anything answered it; this is the release that answers it. What closed the gap is the retirement of the pull side: `PDM.ResourceManagers.Client` - the gateway PDM dialled a manager over - is deleted, and with it the file provider abstraction, the manifest and health sources, the connection routes that called `/v1/auth`, the capability grants that gated calls PDM no longer makes and the `Endpoint` column that said where to make them. A deployment can no longer reach a resource manager, which is what a build serving 2.0 has to be true of before it may say so. `PDM-Core-Version` now negotiates inside the 2.0 major only: a client asking for 1.x is refused with `400 unsupported_core_version` naming both sides, rather than served an API that has none of the operations it was written against. | Core API | 2.0 | **The core only answers, so a resource manager pushes (#254, #274).** The direction of the whole integration reverses: PDM makes no call to a resource manager at all, so a manager walks its own resource and feeds PDM what it finds. **Added** - `POST /v1/searches/{searchId}/items` declares a batch of enumerated images and is answered per item with `cached`, `needsContent` or `rejected`, which *is* the repeat-scan cache (#230) rather than a hint about it; `PUT /v1/searches/{searchId}/items/{imageRef}/content` sends the bytes of one image, streaming and resumable and idempotent on the reference; `POST /v1/searches/{searchId}/complete` ends the walk, replacing the `isLast` PDM used to read off a batch it had pulled; `POST /v1/images/gone` is how a manager reports that a reference no longer exists; `ingest_credits` on `GET /v1/stream` is the backpressure the reversal owed, an absolute count of images PDM will take the bytes of; and two scopes, `searches:ingest` and `images:forget`. **Removed** - `GET /v1/images/{imageId}/thumbnail` and `.../content`, because the frontend that renders a tile belongs to the manager that owns the file; `POST /v1/files/recycle`, `/delete` and `/move`, because the manager deletes its own file and reports it, and PDM can no longer verify anything it would have asked for - note that the `newImageRef` half of a move has **no replacement**, so a manager whose references are paths reports them gone and the photographs leave their duplicate groups until a rescan, which is a known gap and an additive one to close; and `POST /v1/tokens/capability` and `POST /v1/tokens/media`, whose retention (#253) named this exact moment as its trigger. With them go the capability and media token classes, the scopes `images:read`, `files:recycle`, `files:delete` and `files:move`, and five error codes nothing can produce any more. **Changed** - `ResultImage` loses `name` (which was *required*), `displayPath`, `available` and `trashed`, and `imageRef` becomes required in their place; `availabilityChecked` goes from a page of groups and `connectionState` from a result; `GET /v1/resource-managers` stops reporting capabilities, health, connection and contract version, because PDM has none of them; `recursive` and `cacheFolderRef` leave `StartSearchRequest` (how deep to walk is the caller's, and a wider cache is `cacheOnly` on an item, because PDM has no concept of a directory); `limits` gains `maxItemsPerBatch`, `maxImageBytes`, `maxIngestCredits` and `ingestPartialSeconds` and loses the two token lifetimes; and a `Ref` may no longer be `.` or `..`, now that one appears in a path segment. **Two things about the version itself.** The twelve-month overlap [`docs/version-compatibility.md`](version-compatibility.md) section 3.2 asks for between majors **is not owed here, and this is where that is written down rather than left to be inferred**: the SDK is not published outside this repository (#192 is open), so the only clients of `/core/v1` are the four resource managers built in it - the same reasoning #197 used when it withdrew the UI protocol at 1.0. And the **`/v1` path prefix did not move**. A prefix exists so two majors can be served side by side, which is exactly the overlap that is not being run; what a deployment speaks is read from `PDM-Core-Version`, which refuses a major it does not speak with `400 unsupported_core_version` naming both. | **Nothing - this row records a document, not a release; the release that serves it is the row above.** It was written before #275 (the ingest path), #276 (the managers push), #277 (reads move to the manager) and #278 (the pull side retires) had landed, so that each of them implemented something decided rather than deciding as it went. When it does, an integration written against 1.x stops working, which is what a major means and why this one was affordable. What to do then, in order: exchange your credentials as usual and ask for `searches:ingest`; open a search with `POST /v1/searches` as before; walk your own source and declare each batch, uploading only what you are told is needed; call `complete` when the walk ends; watch `ingest_credits` on the stream and never send without one. Serve your own thumbnails, your own names and your own file operations to your own frontend - you already have all of them, and PDM never had any of them without asking you first. |

| UI message protocol | 1.0 | The protocol became checkable (#151). No change to it. `front-end/conformance` mounts a workspace cross-origin in a real browser, plays the host, and evaluates every message the guest sends against this schema - the same evaluation both sides are told to perform on receipt. It also mounts the workspace a second time with a `hostOrigin` that is not itself, which is the only way to observe that `guest.ready` was addressed to the host rather than to `'*'`. | Nothing. A workspace that posts to the `hostOrigin` on its frame URL, as 1.0 already requires, passes. |
| UI message protocol | 1.0 | **Retired (#197).** `resource-manager-ui-protocol.v1.schema.json` is removed from this repository, and so are the tool that checked it (`front-end/conformance`) and the workspace in the `dotnet new` template. [#139](https://github.com/Iskandarus/photo-duplicates-manager/issues/139) was revised: a resource manager is a separate application, and PDM renders the entire user interface rather than mounting anybody else's page. No deprecation window, because there is nothing to strand - the shell that would have mounted a workspace was never built (#152, closed), the SDK is not published outside this repository yet (#192), and no manager serves one. | Nothing, unless you had started building a workspace against it - in which case stop, and read `docs/writing-a-resource-manager.md`, which is now the whole of what you implement. Your manager serves the data contract; anything you want to show the user, you show in your own application, which calls PDM's core API with the client credentials your registration was issued. |
| Resource manager API | 1.2 | **One `userRef` may have several accounts.** `auth/status` gains `accounts[]`, each entry carrying an `accountRef` the resource manager mints and PDM names it by afterwards; every user-scoped operation gains an optional `accountRef` query parameter; and `supportsMultipleAccounts` stops being reserved and starts meaning what it says (#229, closing the half of #148 that needed it). The `accountRef` is the manager's own opaque value, like `imageRef` and `folderRef` and unlike `userRef`: an account at somebody else's service is the manager's to name, and the account id at the upstream service still never crosses this boundary. | Nothing. A manager that leaves `supportsMultipleAccounts` false is never sent an `accountRef`, and one that is sent it anyway may ignore it - absent and unrecognised both mean the account the call already acted on. Implement it when you want a user to link two accounts at once: list them in `auth/status`, act on the named one, and answer `forbidden` for an `accountRef` you did not mint rather than falling back to the default. |
| Resource manager API | 1.1 | The manifest's `ui` block is deprecated and ignored (#197), for the reason in the row above. It is kept rather than removed because removing a field is a major, and a major buys a version fork in every implementation for something PDM can simply ignore. **`ui.fallbackSource` moves to the root of the manifest** and is the one part of that block that is not deprecated: it labels the source input PDM renders, which is now the only way a user names a folder. The copy inside `ui` is read for one release, and a manifest sending both is answered from the root. One sentence that lived inside `ui` is also now unconditional: a resource manager **must** accept human-enterable values as a `folderRef`. | Move `fallbackSource` up one level when convenient - nothing breaks until the old place is removed, which is a later release and will have its own row. Beyond that, nothing if your refs are already something a person could type. If they are base64url, the box hands your user `QzpccGhvdG9zXDIwMjQ` to type and that is now the only way in: accept what a person would naturally write and normalise it internally. Keep sending the rest of `ui` if you like; nothing reads it. |
| Core API | 1.2 | **`supportsPicker` is deprecated and pinned to `false` (#150.)** It was computed from the manifest's `ui` declaration, which resource manager contract 1.1 deprecated, so it could report `true` for a frame nothing will ever mount - and whether a folder picker exists was never this API's question. It is a fact about a resource manager's own backend, asked there. The field is pinned rather than removed for the same reason 1.1 kept the `ui` block: removing a field from a published contract is a major version, and a major buys a version fork in every implementation for something PDM can simply stop meaning. | Nothing, unless you branch on it. If you do, take the branch out: the answer is now always `false`, which is the same answer you would get from a manager that mounts nothing - accept a human-entered `folderRef`, which every resource manager is obliged to understand. |
